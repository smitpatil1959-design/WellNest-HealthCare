# Disposable live backend checks

The user authorized seven temporary demo accounts, their synthetic workflows, and removal afterward. The runner is `scripts/live-demo-qa.mjs`. Its default invocation only prints the plan. `--run` executes against the explicitly allowlisted WellNest deployment and Supabase project. Server credentials are read privately from `.env.local`; do not paste them into chat or commit them.

The runner creates one account for each portal and four isolated organizations. Staff roles and memberships are provisioned for synthetic testing; this does not test real professional credential approval. Each account signs in normally with a randomly generated password. Passwords, tokens and authenticator secrets remain in memory. Demo addresses use the reserved `example.test` domain and no sign-up emails are sent. Email/SMS preferences are disabled and no delivery worker is invoked.

Clinical workflows call the real deployed API with those authenticated sessions. Administrative database access is used for temporary provisioning, narrowly scoped assertions, the demo hospital membership change, and cleanup. It does not replace the application's authorization checks in the workflow requests. Local fixture tests and live checks are reported separately.

The run covers portal reads, menu data and settings endpoints, consent approval/revocation, simultaneous booking contention, overlapping slots, rescheduling/cancellation, attributed consultation, recipient-scoped record sharing, prescriptions/dispensing, inventory conflicts, hospital admission/discharge, structured lab release, private upload restrictions, insurance claims, privacy requests/export, support, account suspension, and real TOTP/AAL2 protection. These checks do not guarantee every UI state or absence of all defects.

An ignored manifest under `node_modules/.tmp/live-qa/<run-id>.json` contains IDs, results and cleanup status; it contains no passwords or tokens. Cleanup validates the exact run marker on each account and the tracked organization names before deleting anything. It removes only that run's uploaded objects and dependent rows, then verifies account and organization removal. An interrupted cleanup can be resumed with `node scripts/live-demo-qa.mjs --cleanup <run-id>`. Keep the manifest until cleanup is verified. Existing personal Google accounts and their earlier TEST ONLY audit artifacts are outside this cleanup scope.

`--prepare-storage` provisions the application's private `medical-reports-private` bucket when absent. The bucket is retained for the website; test objects are removed. It has public access disabled, a 3 MB limit, and PDF/JPEG/PNG restrictions. It does not activate a malware scanning service.

The live tests corrected a missing recipient on report shares and the missing patient insurance route. Missing private upload storage was provisioned. The unrelated legacy restore hook was removed, but the calendar timeout persisted: that hook was not its cause. The calendar failure matched Supabase's documented PostgREST retry loop for custom SQLSTATE 40001 business errors. Migration 015 changes only those business conflicts in five existing functions to PT409; application handlers accept both codes during rollout. The operator applied it on 2026-11-05; the subsequent live contention, overlap, rescheduling, cancellation and slot-closure checks passed. [Supabase explanation](https://supabase.com/kb/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions).

Run `supabase/verification/migration_015_preflight.sql`, then `supabase/migrations/015_non_retryable_workflow_conflicts.sql`. If the preflight lists aged active calls, run `supabase/verification/migration_015_clear_stuck_calls.sql` afterward. That operational script cancels only active authenticator calls to the five affected workflows older than 90 seconds; unfinished transactions roll back. It does not restart the project or delete records. The application request lifetime is 60 seconds. Check the read-only preflight again afterward. Never repeat the contention test against the old functions.

Read `live-demo-test-report.md` for the latest actual run. Email/SMS receipt, a hosted scanner's clean-file verdicts, and production backup restoration remain external acceptance work. No providers or paid resources are activated by this runner. Portal refresh uses polling rather than WebSocket realtime subscriptions.
